CNC Pay — end-to-end flow

Aurorify is the example merchant used throughout — a third-party storefront, not part of CNC Portal, that already has a CNC Portal team account (and so already has a Bank.sol treasury). This walks through setting up the gate on their checkout page to the money landing in that treasury.

1

Aurorify sets up the gate

Picks settlement modes and accepted tokens; gets back a publishable key; drops one script tag on their checkout page.

2

A customer lands on checkout

The widget loads Aurorify's config with that key, and opens a pending payment record so there's an id to track.

3

Customer connects their wallet and reviews

Amount, mode, and fee are shown; the widget reads their balance directly from the chain.

4

Customer pays

Their own wallet signs and broadcasts the transaction straight to Polygon. CNC Pay never touches the funds or holds a key.

5

Widget reports the transaction hash

Just a pointer — "this hash belongs to this payment" — not proof on its own.

6

CNC Pay checks that one transaction

Polls it until it's mined, then reads the receipt to confirm it actually matches — right contract, right amount, right recipient.

7

Payment is marked paid — Aurorify finds out one of two ways

Chosen once, in the gate config. Both end at the same trusted status endpoint.

Default

Ping, then recheck

CNC Pay pings Aurorify's URL with just a payment id — no payload, nothing to verify. Their backend calls the status endpoint to get the real answer. No secret, no signing code to write.

Opt-in

Signed webhook

The full status is pushed directly, signed so it can be trusted without an extra round-trip. Needs signature-verification code on Aurorify's side — worth it only if that extra call actually matters to them.

8

The money is already there

Net of the platform fee, sitting in Aurorify's own Bank — the same treasury they already manage in CNC Portal.

What's real today: the widget pattern, Bank.sol, AdCampaignManager.sol, FeeCollector.sol. Everything else above — the config, the payment record, both notification paths — is designed, not built. Most merchants never touch a signing secret at all: the ping carries no payload, so the publishable key alone covers checking a payment they already know the id of. A secret only enters the picture for merchants who opt into the signed webhook.
